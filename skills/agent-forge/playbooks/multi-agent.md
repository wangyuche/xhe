# Playbook:多個 agent 同時做事

只在**同時有多個 agent 要做事**時適用。單一 agent 循序工作,就在目前分支進行。

依據:pstack 的 `swarm`、`orchestrate` 原文(cursor/plugins 的 pstack)。標「自訂」的是本專案自己加的,不是 pstack 原文。

## 角色

- **協調者(coordinator):** 只規劃、派工、驗收,**不寫程式、不改檔案**。
- **owner:** 負責一個單位(例如一個 PR 或一個分支),是該分支**唯一的寫入者**。只有 owner 能 push、rebase。
- **verifier:** 驗證者,不能是作者,要用不同模型家族。

## 派工

1. **先跑一個單位,再扇出。** 先讓一個任務走完 kickoff、owner、verifier、merge,確認流程沒問題再展開。啟動有缺陷時,代價是一個 agent,不是一堆。
2. **簡報要自足。** 每個 worker 看不到其他 worker,所以簡報必須包含:目標、可寫和不可寫的路徑、禁止的動作、證明完成的證據、要回報什麼。說不出證據,代表任務還沒定義好,先不要派。
3. **新工作給新 worker。** 只有當新工作需要既有的狀態(例如它的 checkout 或執行中的行程)時,才延用或 fork 舊 worker。只為了追問同一件事才傳訊息給 worker,不要為了「看一下進度」傳訊息。
4. **傳檔案位置,不要把內容整份貼進去。**
5. **寫入者各自要有可寫的輸出。** 可能動到同一批檔案的 worker,要分開(自訂:用獨立 git worktree 和分支,分支名稱如 `agent/<name>/<task>`)。
   - **判斷能不能開 worktree,要在每個 worker 的目標目錄跑 `git -C <目標目錄> rev-parse --show-toplevel`**(自訂,2026-11-22),不要看 session 根目錄或環境說明的「Is a git repository」:monorepo 的外層常不是 git、子專案才是。有輸出就開 worktree;真的不是 git 時(`scope.sh` 也不能用),可能動到同一目錄的 worker 改成循序,或給每個 worker 不重疊的輸出目錄並在簡報寫明。
     > 失敗範例(MahjongParty 開房券):環境說明寫外層不是 git,協調者沒查 `lobby/` 就讓後端、後台、大廳前端三個 owner 共用一個 checkout;5 份回報的 scope 檢查都被別人的改動算成 OUT、標 ISSUES。
6. **派工前先列檔案範圍,有重疊就改成循序**(自訂)。分支只能隔離,不能消除衝突。
7. 同時進行的 worker 數量要有上限,一個做完再補下一個。
8. **派工前逐條對照決策表與情境**(自訂,2026-11-21):使用者回答過的每一條決策,都要對應到某個情境編號、且出現在某個 owner 的簡報裡;要新增的需求先交情境設計者編號,不用沒編號的文字交代。判定標準(特別是並發的狀態碼分佈、不變量)一律引用情境的 Then 或 owner 產出的表(例如 backend-owner 的端點驗證表),協調者不自己另寫。
   > 失敗範例(fortest 登入 + RBAC):簡報漏了決策 Q8 的改角色 / 停用畫面;追加需求沒編號,前端自訂 `RBAC-Q8-UI:`,verifier BLOCKED;verifier 簡報缺端點範例又 BLOCKED;協調者自己寫的並發判定標準兩次錯(測不到 409、`401 ≤ 5` 與 Q6 矛盾)。

## 混用多種技術時(自訂)

同一個專案混用多種前端技術時,不要為每種技術各造一個 agent。用一個通用角色(例如 `frontend-owner`)加上各技術的獨立 skill。技術 skill 只放該技術獨有的規則,通用規則不重複寫。

技術 skill 用 `paths` 限定檔案範圍,碰到符合的檔案時才出現,不用手動指定。例如:

```yaml
---
name: stack-react
description: React 規則。碰到 .tsx 檔案時使用。
paths: ["**/*.tsx"]
---
```

實測(Claude Code 2.1.325):設了 `paths` 的 skill 平常不在清單裡,讀到符合的檔案後才出現,出現時只有名稱和說明進 context,內文要被呼叫才載入。限制:只測過 `**/*.tsx` 這一種寫法,也只驗證了「出現在清單」,沒驗證模型會不會在該用時自動呼叫。

只有下列任一項成立才拆成不同 agent:驗證方式完全不同(瀏覽器對模擬器)、可寫路徑或工具不同、要平行做且互不重疊、模型或推理強度需求不同。

## 不確定設計方向時

一次嘗試可能把形狀鎖錯時,用 `playbooks/arena.md`(要用時才讀,讀就完整讀)。

## 開始執行時(依據 pstack multi-phase-plan、orchestrate)

- 使用者說「開始」時,協調者重新讀一次這份 playbook,並記下 skill 目錄的版本指紋(算法見 `SKILL.md`「檔案位置」)。
- 專案進行中如果版本指紋變了,在下一次回報時告訴使用者,由使用者決定是否重跑受影響的單位。2026-11-21 之前記錄的指紋是舊算法(絕對路徑),不能直接比:先用新算法重算一次當基準,這不算規則變更。
- 協調者的 context 只留摘要;大量內容(長檔案、原始輸出)交給 subagent 處理。

## 收攏與審查

- 等所有 worker 完成,收攏成**一份報告**:結果表、問題摘要、缺口或中途退出者。不要貼 worker 的原始輸出。
- 每個 worker 回報 `PASS`、`ISSUES` 或 `BLOCKED`,並附證據。能證明有問題就**列出所有能證明的問題**,不只第一個。
- **簡報要求的證據沒回報,就丟棄這份結果並重派一次。** 第二次還缺,就記為缺口。**缺口不算通過。**
- **驗證者要讀 diff 或實際產出,不只看 worker 的摘要。** 綠燈 CI 只是輸入,不是結論。
- **一個問題要成立,必須有一次實際執行來證明**(指令、實際輸出、應有的輸出)。找不到問題也是有效的結果。
- **一個結論只對應一個 head SHA。** 之後有新的 push,就要重新驗證。
- 你要為每個 worker 的成果負責:審過再寫自己的總結,不照抄 worker 的回報。

## 卡住與重試

- 判斷 worker 是否卡住,看它的 push 和實際產出,不看它自己說的狀態。
- 依原因重試:context 或記憶體不夠就縮小範圍;連線中斷就用同一份簡報重派;工具錯誤就換模型。
- 重試兩次還不行,就放棄該單位並重新規劃。
- 晚回來的 worker,先對照目前狀態,再把有價值的發現轉給新 worker。

## 什麼時候問使用者

只在下列情況問:不可逆或對外的動作、沒有實驗能決定的產品或偏好選擇、重新規劃後仍走不通的死路。其他事情自己處理,不要問:rebase、重試、CI 不穩、「要不要繼續」。

## 合併與 push(自訂,依使用者指示)

- 在本地分支 commit 不用問。
- **合併的條件:** 驗證通過、head SHA 沒變、測試全部通過。
- **push 的條件:** 已合併,且測試全部通過。條件滿足才能 push,不滿足就不 push。
- **這些仍然要先問使用者:** force-push、刪除分支、部署、刪資料、對外發訊息。
- 衝突交給該分支的 owner 處理,涉及取捨時才問使用者。
- worker 預設只 commit 到自己的分支,不直接動主分支。
- 沒有設定遠端的練習資料夾,沒有 push 這一步,做到本地合併即可。
