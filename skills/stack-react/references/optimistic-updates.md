# 列表上的修改操作與樂觀更新(需要時才讀)

元件會在列表裡直接修改資料(改角色、停用、切換狀態),或有 `並發` 類型的元件情境時,實作前先讀完這份。

來源:2026-11-21 fortest 使用者列表,4 輪 code review 每輪都在這裡找到問題。

## 1. 同一列一次只有一個請求
- 用 `useRef` 記錄進行中的列 id(state 來不及:連點時第二次 render 前就會再觸發),進行中時 `updateUser` 直接 return。
- 該列所有操作(下拉、按鈕、**確認框裡的確定按鈕**)在 pending 時都 `disabled`,點擊處理裡再檢查一次。請求一開始就關掉確認框,結束後不要自己重新打開。
  > 失敗範例:確認框開著時改了角色(PATCH #1 進行中),確認框裡的「確定停用」仍可按,送出 PATCH #2;#1 失敗時用整列舊快照還原,蓋掉 #2 的成功結果。

## 2. 失敗時只還原這次改的欄位
- 不要存整列快照再整列蓋回。記下「這次請求改了哪些欄位、原值是什麼」,失敗時把這些欄位套回**目前**的列狀態。
- 若該列在請求期間已被重新載入成新的伺服器值(不再是樂觀值),就不要還原,保留新值。

## 3. 重新載入不能用舊快照覆蓋較新的結果
- 每次 GET 開始時建立一份「本次載入期間成功的 PATCH」紀錄;GET 回來時,這些列用 PATCH 回傳的值。
- 仍在進行中的樂觀修改也要在 GET 結果上重新套用,不然畫面會先跳回舊值再跳回新值。
- 換頁或卸載時紀錄作廢。

## 4. 權限錯誤要重新取得權限
- 列操作或表單送出收到 403:顯示「沒有權限」,呼叫 `router.refresh()` 讓 server 重新算權限(操作欄、新增按鈕會消失),並重新載入列表。404 重新載入列表。
- 列操作的錯誤訊息在換頁、按重試時清掉;403 / 404 觸發的自動重新載入不要清,否則使用者看不到訊息。

## 5. 長度檢查要和後端一致
- 字元數用 `[...value].length`(Unicode code point),不用 `value.length`(UTF-16 單位:4 個 emoji 會算成 8)。
- 後端有 byte 上限(bcrypt 72 bytes)時另外檢查 `new TextEncoder().encode(value).length`。
- 不用 `minLength` / `maxLength` 屬性做這類檢查(瀏覽器以 UTF-16 計,`maxLength` 還會默默截斷)。違反時在欄位下方顯示具體規則。

## 測試
每一條至少一個元件測試,用可控的 Promise 讓 PATCH / GET 卡住,做出交錯:
- 確認框開著 → 改角色(PATCH 掛起)→「確定停用」不能送出第二個 PATCH。
- 列 1 PATCH 404 觸發重新載入(GET 掛起)→ 列 2 PATCH 成功 → GET 回傳舊值 → 列 2 仍顯示新值。
- 403 時有呼叫 `router.refresh`。
- 4 個 emoji、30 個中文字的密碼不能送出。
