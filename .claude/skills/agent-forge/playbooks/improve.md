# Playbook:改進(reflect / correct)

agent 造完之後會繼續被使用。要有機制回頭看它的成果,把教訓留下來。依據:pstack 的 `reflect`、`correct` 與 principle「Encode Lessons in Structure」。標「自訂」的是本專案自己加的。

## 觸發

- 你說「reflect」或糾正了某個 agent 的行為。
- 一個 agent 完成一批工作後,由 verifier 審過成果。

pstack 的 `/reflect`、`/correct` 本身都是手動觸發。目前本專案也只做手動,沒有排程。

## 判斷什麼算教訓

- **一次性的事不是教訓。** 只出現一次、且已被現有規則涵蓋的,不處理。
- **同一類錯誤發生過兩次,才算一個「錯誤類別」。** 這時才動手改。
- 對話或紀錄太瑣碎、離題時,直接跳過。

## 怎麼改:能用結構擋的,就不要只寫文字

依下列順序,選**能做到的最高層**:

1. **結構:** 讓錯誤不可能發生(例如範本把欄位設成必填、移除 agent 不該有的工具)。
2. **檢查:** 加一個會失敗的檢查,錯誤訊息要指出該改用哪個檔案或做法(例如在 `spec-reviewer` 加一條檢查項目、在 `agent-tester` 加一個測試情境)。
3. **測試:** 修正會在行為壞掉時仍然通過的測試。
4. **文字規則:** 最後才用,只用在必須靠判斷的事,因為 agent 略過文字規則時不會有任何東西失敗。真的只能寫文字時,把指示放得更顯眼,並附一個失敗範例。

「如果解法是結構性的,就只用結構性的解法。重複寫指示只是症狀。」

## 流程

1. 找出錯誤類別:讀紀錄、你的糾正、`agent-tester` 與 verifier 的回報。
2. 為每個類別選最高可行的層級,做出修改。
3. **證明新檢查有效:** 拿一個過去真實發生的錯誤,證明新檢查會擋住它。
4. **改完重測:** 改過的 agent 要重跑原本失敗的情境,有證據才算改善。
5. **每個錯誤類別一個 commit**(commit 前先照下方「怎麼套用」徵求同意)。
6. 規則放進規則表。規則對應的錯誤已經不可能發生時,就把規則移除。

## 規則表(來自 correct)

維護 `.claude/agent-specs/RULES.md`,每條規則成對記錄「規則」與「由什麼強制」:

| 規則 | 強制方式 | 來源(哪次錯誤) |
|---|---|---|
| ... | 範本必填欄位 / 檢查項目 / 測試情境 / 僅文字 | ... |

某條規則已存在、但「僅文字」,而錯誤又發生了,就視為重複,這次改成更高層的強制方式。

## 怎麼套用

- **不要自動套用。** 先把完整的改動清單(接受、拒絕、暫緩)給使用者看,同意才改。
- 小改(一行規則或更正一個事實)直接改。大改(新增一整段、超過約 10 行)先給使用者看改動內容。
- 不 push、不開 PR。
- 暫緩項目記在 `.claude/agent-specs/RULES.md` 的「待辦」區。

## 自訂:每個 agent 的使用紀錄

- `.claude/agent-specs/<name>.log.md`:每次使用後由 verifier 加一行,包含任務、結果(PASS、ISSUES、BLOCKED)、證據、發現的問題。
- 這是找出「同類錯誤是否發生兩次」的原始資料。pstack 原文沒有專門的紀錄庫,這是本專案的補充。
- 紀錄會越積越多,定期整理,只留還有用的。

## 自訂:排程

目前不排程。**第一次完成一輪改進後,問使用者要不要排程**(例如定期產出改動清單等批准),使用者說要才設定。排程只產出清單,不自動套用。
