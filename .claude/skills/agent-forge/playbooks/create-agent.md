# Playbook:造一個專業 agent

流程固定,依序走 Intake → Spec → Build → Verify,不跳關。

## 階段 1:Intake(訪談)

目標:搞清楚使用者要的 agent 到底是什麼。**先分類再問**:能從使用者已說的內容、這個專案的檔案,或小實驗查出來的事,自己查,不要問。只問真正的產品或偏好選擇,而且從最關鍵的開始,不要丟一整份問卷。

必須釐清的項目:

- **領域與任務**:這個 agent 主要做什麼?不做什麼?
- **使用者與觸發時機**:誰會用?在什麼情況下被呼叫?
- **輸入與輸出**:拿到什麼、交出什麼?格式有要求嗎?
- **成功標準**:怎樣算做得好?有沒有一個可以檢查的具體例子?
- **限制與禁忌**:不能碰的檔案、不能做的動作、語氣和風格要求。
- **需要的工具**:要讀寫檔案、跑指令、上網,還是只要思考?

使用者已經講過的就不要再問。資訊夠寫規格時就停止訪談。

## 階段 2:Spec(規格)

用 `.claude/templates/agent-template.md` 的「規格區」格式,寫出一頁規格,存到 `.claude/agent-specs/<agent-name>.md`。

接著呼叫 `spec-reviewer` subagent 審規格,把規格檔路徑給它。它會回報缺漏、含糊處和過度授權的工具。

- 有問題:修正規格後再審(最多 3 輪,自訂的上限)。
- 通過後,把規格摘要給使用者看,**等使用者確認才進入 Build**。

## 階段 3:Build(生成)

依確認過的規格產生檔案:

1. `.claude/agents/<agent-name>.md`:agent 本體,依範本寫 frontmatter 和 system prompt。
2. 只在規格確實需要時,才額外生成 `.claude/skills/<skill-name>/SKILL.md`。不要為了看起來完整而多做。

寫 system prompt 的規則:

- 開頭一句話講清楚角色和邊界。
- 工作流程寫成有順序的步驟,每步要有完成條件。
- 工具只給規格列出的,多一個都不給。
- 明確寫「遇到什麼情況要停下來問使用者」。
- 輸出格式要具體,最好附一個範例。
- 把規格裡的成功標準原樣寫進 agent,讓它知道自己要被怎麼檢查。

## 階段 4:Verify(驗證)

1. 依規格的成功標準,設計 3 到 5 個測試情境,至少包含:一般情況、邊界情況、一個「不該做」的情況(測禁忌)。存到 `.claude/agent-specs/<agent-name>.tests.md`。
2. 呼叫 `agent-tester` subagent,給它 agent 檔案路徑和測試檔路徑。它會扮演該 agent 跑每個情境,並逐條對照成功標準判定通過或失敗。注意它是「扮演」,結果可能比真實情況樂觀;沒有證據或無法判定的情境,視為缺口,**缺口不算通過**。
3. **一項問題要成立,必須有一次實際執行來證明**:附上指令、實際輸出,以及依規格應有的輸出(依據 pstack `interrogate`)。沒跑過的推測不列。找不到問題也是有效的結果。
4. 有失敗:根據失敗證據修改 agent,重跑失敗的情境。最多 3 輪(自訂的上限)。3 輪後仍失敗,就如實告訴使用者卡在哪裡,不要硬說完成。
5. 全部通過後,回報給使用者:
   - 新 agent 的名稱與檔案位置
   - 每個測試情境的結果(附證據摘要)
   - 已知限制
   - 如何呼叫它
