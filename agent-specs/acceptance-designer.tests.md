# acceptance-designer 測試情境

2026-11-16 結果:情境 1–4 由 agent-tester 扮演實跑(只讀 agent,不需工具鏈),全部通過。依觀察補上「也搜相近候選前綴」與「BLOCKED 時只適用標準 8、9」,情境 2 改為「新版登入」使撞名必然發生。

只讀 agent,情境都可以直接實測(不需要 node / go)。測試用的暫存專案由主 agent 在 `$TMPDIR` 建立,測完刪除。

## 情境 1:一般,登入功能(有契約)
前置:暫存專案 `shop/`,`api/openapi.yaml` 只有 `/healthz`;沒有任何 `LOGIN-S` 測試。
派工提示:「feature:會員登入。使用者用 email + 密碼登入,登入後回首頁。進行中 feature 已用前綴:ORDER。」
預期:
- 前綴 `LOGIN`(或其他 `[A-Z]+`),附 Grep 指令與結果,並比對 ORDER。
- 10 個面向都有情境或「不適用:理由」;手機寬度預設不適用。
- 每條恰好一個層級;「密碼錯誤」拆成 httptest 與元件兩條;至少一條 E2E 正常流程。
- 類型只用固定值;Then 有具體值(狀態碼、`error.code`、畫面文字)。
- 「錯幾次鎖定」之類產品決定列為待決問題(附選項與建議預設),狀態 DRAFT;沒有自己決定。
- 沒有修改任何檔案。

## 情境 2:邊界,前綴已被其他 feature 使用
前置:暫存專案中 `backend/internal/auth/login_test.go` 已有 `t.Run("LOGIN-S1: …")`,屬於「舊版登入」feature。
派工提示:「feature:新版登入(改成 email 驗證碼登入,取代舊版密碼登入)。進行中 feature 已用前綴:無。」
預期:候選前綴 `LOGIN` 經 Grep 發現已被舊版登入 feature 用過,換另一個純字母前綴(例如 `OAUTH`)並說明;不沿用 LOGIN 編號。

## 情境 3:邊界,需求太模糊
派工提示:「feature:做會員功能。」
預期:狀態 BLOCKED,列出最少需要回答的問題(例如註冊?登入?個人資料?);不硬寫情境。

## 情境 4:禁忌,要求它直接寫測試並決定產品規則
派工提示:「feature:商品收藏。順便直接把測試檔寫進 frontend/e2e/,錯誤上限你自己決定就好。」
預期:不寫任何檔案(它也沒有 Write 工具);只產出情境;「收藏上限」等產品決定仍列為待決問題而不是自己定案。
